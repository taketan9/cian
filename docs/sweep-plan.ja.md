# 総ざらいの計画 ── 固まる・落ちる・間違う を出し切る

この文書は、cian の不具合を出し切るための**実施計画**です。実施した結果は
ここには書きません。見つけたものは `sweep-findings.ja.md`（未作成）に、直した
ものは [`gui/REQUESTS.ja.md`](../gui/REQUESTS.ja.md) に記録します。

計画の対象は「結構固まったり、変な挙動をすることが多い」という実務での印象です。
固まる現象を先頭に置いたのは、**現在の検査がその種類の故障を1件も見ていない**
ためです。理由は次の章に書きます。

## 1. なぜ固まる現象が見えていないか

次の3点は、コードを読んで確かめた事実です。

**① エンジンは要求を1本ずつ順に処理します。** `crates/cian-server/src/main.rs`
の `main()` は標準入力を1行ずつ読み、1つの要求を処理し終えてから次を読みます。
したがって1つの要求が返らない場合、Electron 版の画面は全体が応答しなくなります。

**② 待ちに上限がありません。** 要求の処理から呼ぶもののうち、次の3つは時間の
上限を持ちません。

| 待つもの | 上限 | 件数の取り方 |
| --- | --- | --- |
| SFTP の通信（`crates/cian-scp/src/lib.rs`） | **ありません。** 接続・一覧・転送のどれにも時間制限を設定していません（`set_timeout` の呼び出しがありません） | — |
| 子プロセスの終了待ち | **ありません。** `crates/cian-core/src/proc.rs` の `quiet()` は Windows の画面を隠すだけで、待ちの上限を持ちません | `grep -rF ".output()" crates/*/src --include="*.rs" \| grep -v tests.rs` |
| ファイルを丸ごと読む `read_to_string()` | **ありません。** 大きさと種類を確認していません | `grep -rF "read_to_string" crates/*/src --include="*.rs" \| grep -v tests.rs` |

子プロセスの内訳は Git・Subversion・`osascript`・Python の存在確認・接続先の
`password_cmd` です。**`password_cmd` は利用者が設定するコマンドです。**
端末版だけで呼ぶもの（書体の確認と IME の確認）は、同じ種類の故障ですが
止まる相手が端末版の画面になります。

**SFTP に上限が無いことは、会社の環境で最初に疑う点です。** 接続先が応答しない
場合、オペレーティングシステムの既定の時間（数十秒から数分）まで待ちます。
その間、Electron 版の画面は全体が応答しません。

**③ 現在の検査は、固まった状態と何も起きない状態を区別できません。**

| ツール | 生存の判定 | 固まった場合の見え方 |
| --- | --- | --- |
| `scripts/sweep.py` | プロセスが終了していないか | 「反応なし」に分類されます |
| `scripts/tui-drive.py` | 画面が変わったか | 「動かなかったキー」に数えられます |
| `gui/drive.js` | 例外が出たか | 時間の上限が無いため、ツールごと停止します |

**`gui/drive.js` の「動かなかったキー」は 66 件から 71 件の間で揺れます。**
この幅の中に、本物の固まりが隠れられます。

> **注意**
> 計画の第1段を「時間の上限を入れる」にしているのは、この③のためです。
> 上限の無い検査は、固まる現象を永久に見逃します。

## 2. 故障を4種類に分けます

| 種類 | 症状 | 現在の測定方法 | 足すもの |
| --- | --- | --- | --- |
| A 固まる | 操作しても返りません | ありません（「反応なし」に混ざります） | 要求ごとの上限。超えたら失敗として報告します |
| B 落ちる | 終了する・画面が壊れます | 窓は例外の件数、端末はプロセスの終了 | 想定外の入力を与えます |
| C 間違う | 違うものが表示されます | `sweep.py`・`kotoba.py`・`widths.py`・`audit.py` | **状態の掛け合わせ**（現在どのツールも見ていません） |
| D 環境差 | 会社の環境だけで起きます | CI の型検査と、本人の確認 | 手元で再現できる形に寄せます |

B の規模は、テストを除いて `unwrap()` が 828 か所、`as usize` が 181 か所、
添字の `[0]` が 172 か所です。**この3つはいずれも、想定外の入力で終了します。**

## 3. 段取り

上から順に実施します。第1段を先に終えてください。第1段が無い状態で第3段を
実施すると、固まった結果が「反応なし」として記録されます。

### 第1段 時間の上限を入れます（ツールの側）

| 対象 | 変更 |
| --- | --- |
| `gui/drive.js` | 要求ごとに上限を設け、超えた場合は例外として数えます |
| `scripts/tui-drive.py`・`scripts/sweep.py` | 打鍵から画面が変わるまでを測り、上限を超えた場合は生存とは別の区分で報告します |
| エンジン | 要求ごとの所要時間を診断記録（`crates/cian-core/src/log.rs`）に書きます |

**上限の既定値は決めていません。** 重い操作（容量分析・検索・書庫の作成）は
正当に数秒かかるため、操作ごとに分ける必要があります。

### 第2段 上限の無い待ちを一覧にします（静的な検査）

`deadline.py`（未作成）を追加します。確認するのは次の3点です。

1. 子プロセスの起動が `quiet()` を通っていること
2. `quiet()` が待ちの上限を持つこと
3. 利用者が指定したパスを `read_to_string()` で丸ごと読んでいないこと

**件数に下限を置きます。** 対象を取りこぼして「所見なし」と報告する故障を
防ぐためです。

### 第3段 わざと詰まらせます（注入）

| 注入するもの | 期待する動作 |
| --- | --- |
| 返らない `password_cmd`（`sleep 600`） | 上限で打ち切り、理由を表示します |
| 接続を受けるだけで応答しないポート | 上限で打ち切ります |
| 名前付きパイプを `a.txt` という名前で置く | 読まずに断ります |
| 2GB の疎ファイル | 先頭だけ読み、読んでいないことを表示します |
| 200,000 件のディレクトリ | 操作を続けられます |
| 読み取り権限の無いファイル | 理由を表示します |
| 壊れた UTF-8 の名前 | 表示が崩れません |
| 端末の大きさ 1x1 と 5x300 | 終了しません |

**期待する動作は3つだけです。** 断ること、理由を表示すること、操作を続け
られること。固まらないことが合格の条件です。

### 第4段 状態を掛け合わせます

状態の軸は次の9つです。`self.popup` が1枠しか無く、別の画面を開くと作業中の
内容が消えた不具合と同じ種類を探します。

ポップアップ／ペインに嵌まった閲覧／シェルに焦点／リモートペイン／書庫の中／
一覧の平坦化／フィルタ／Visual／IME の入力中

**全部の組み合わせは実施しません。** 9軸で 512 通りになるためです。2つの軸の
全組み合わせ（36 通り）に対して、少数の操作（Esc・Enter・Tab・F12・`:`）を
与えます。

### 第5段 既にあるツールを全部通します

`scripts/sweep.py`（全部の verb と `--monkey`）、`gui/drive.js --commands`、
`scripts/tui-drive.py`、機械による検査（`skills/itsumono-check` の一覧）。
**第1段の上限を入れた状態で実施します。**

### 第6段 環境差を、手元で再現できる形に寄せます

| 届かないもの | 寄せ方 |
| --- | --- |
| Windows そのもの | CI の runner で `sweep.py` を実行できるか試します |
| 本人の JIS 配列と IME | `e.code` での対応表を増やします |
| 社内の経路（UNC・長いパス・排他・OneDrive） | 同じ形の偽の経路を作ります |
| 本人の目 | 寄せられません。`UNREACHED.ja.md` に記録します |

## 4. 記録のしかた

見つけたものは `sweep-findings.ja.md`（未作成）に通し番号で記録します。
**直したものだけを [`gui/REQUESTS.ja.md`](../gui/REQUESTS.ja.md) に移します。**
依頼の記録ファイルは「頼まれたことが守られているか」を確認する場所で、未修正の不具合を
置く場所ではないためです。

## 5. 決めていただきたいこと

1. 時間の上限の既定値と、操作ごとの例外（第1段）
2. 第3段と第4段のどちらを先に実施するか
