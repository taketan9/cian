# いつものチェック

実機からの依頼は毎回この3つ。**目視でやらない** ―― 3万行を人が読み返すのは
無理で、読み返したつもりになるのが一番危ない。

## ① 動くか（TUI / GUI の両方）

```bash
cargo test --workspace                                  # 690本ほど・1分
cargo clippy --workspace --all-targets -- -D warnings   # CI と同じ物差し
python3 scripts/tui-drive.py                            # 端末版を**本物の pty で**動かす
node gui/drive.js                                       # 窓版を動かす（例外 0 件が基準）
```

- **`cargo test` だけで済ませない。** CI は `-D warnings` で回る。テストが
  緑でも clippy で赤くなり、3回続けて CI を落としたことがある
- **文書はテストが縛っている。** マニュアル・パレット・README が存在しない
  コマンドを名乗ると `the_manual_never_names_a_command_that_does_not_exist`
  が落ちる。画面に出る文言の句点は
  `nothing_cian_says_ends_in_a_full_stop` が見る。**この2本が緑なら、
  文書の嘘は機械が保証している**
- **GUI は同じレンダラ。** 描画の直しは片方だけ見れば足りることが多いが、
  ウィンドウ固有（フォント・DPI・マウス）を触ったら両方起動する
- **Windows は手元で見られない。** CI のマトリクスを信じ、実機確認は
  月曜にまとめる

### 端末版も実機で動く（2026-09-06 から）

長いこと「端末版は手元で触れない」ことにしていた。**嘘だった。**
`script(1)` で止まるのは、cian が端末へ問い合わせる（DA1・DSR・セル寸法・
kitty graphics）のに素の pty が答えないから。**答えれば動く。**

```bash
python3 -m venv /tmp/cian-tui-env && /tmp/cian-tui-env/bin/pip install pyte
/tmp/cian-tui-env/bin/python scripts/tui-drive.py
/tmp/cian-tui-env/bin/python scripts/tui-drive.py -- j j Space   # 好きな手
```

見るのは**この道具にしか答えられないこと**だけ ── 実際のバイト列、実際の桁、
実際のマウス。中身の判断は `cargo test` が持っている。

| | |
| --- | --- |
| ① 起動 | 問い合わせに答えて、待ちに入らないか |
| ② 枠 | 四隅が描かれているか（**幅を変えて**） |
| ③ 当たり | 日本語のタブ名で、叩いた桁が当たるか |
| ④ 一巡 | 動かなかったキー ── 下端の1行ではなく**画面全部**を比べる |

**日本語でしか出ないものが、ここで4つ出た**（ポップアップのボタンが切れる・
シェルのタブが隣に飛ぶ・右上の角が消える・案内文が色を持たない）。英語は
字数と桁数が同じなので、字で測った箱がたまたま合っていた ── `cargo test` も
目視も通っていた。**桁の話は、桁のある場所でしか出ない。**

## ② 冗長・死にロジック

```bash
python3 scripts/audit.py
```

出るもの:

| 節 | 見るもの |
| --- | --- |
| ① 死にコード | 誰も使っていない `pub`、`#[allow(dead_code)]`、**辿り着けないメニュー項目・コマンド** |
| ② 重複 | 中身が 0.80 以上似ている関数、4回以上出てくる同じ行 |
| ③ 名前 | 画面用語の割れ、コマンド名の複数形 |

**コンパイラが見ているものは見ない。** Rust の `dead_code` は非公開の項目を
自分で見つけるし、cian は `-D warnings` が緑に保たれている。だからこの道具が
見るのは**コンパイラの目が届かないところ**だけだ。実際に死んでいたのは毎回
そこで、リリース直前にはコマンドパレットが**存在しないコマンドを5つ**出して
いた（`:dupes` `:brename` `:macros` `:gitlog` `:toggles`）。関数としては
生きていても、押す道が無ければ死んでいる。

**出たものは「候補」であって「誤り」ではない。** 意図があって分けているものは
`scripts/audit.py` の `TERM_OK` / `PLURAL_OK` に理由つきで書く ―― 消すのでは
なく、**なぜ指摘しないのか**を残す。

## ③ 用語・名前の散らかり

②の③節が機械で見る。加えて**人（AI）が見る**のはここ:

- 同じ概念に別の言葉を使っていないか（「フォルダ」と「ディレクトリ」で実際に割れた）
- **似ているが別のものを混ぜていないか** ―― ペイン（左右の単位）/ 枠（画面上の
  四角）/ パネル（ペインに嵌まったビューア）はすべて別物。シェル（内蔵の枠）と
  端末（cian が乗っている外側）も別物で、**混ぜると IME やキーの説明が壊れる**。
  揃えて「きれいにする」と意味が死ぬ
- 画面に出る文言のハウススタイル。規則は `theme.rs` の `tr()` の doc コメントに
  書いてある（英語は小文字始まり・日本語は敬体・末尾に句点を打たない・
  ダッシュでつながず2文にする・「今のところ」と言わない）

## 直したあと

1. `python3 scripts/audit.py` の候補が、直したか理由を書いたかのどちらかに
   なっていること
2. `cargo test --workspace` と `cargo clippy -- -D warnings` を流し直す
3. **括ったものが再び分かれないよう、テストを1つ足す**（`review_list_key` を
   括ったときは「4つのレビューが同じキーに答える」を足した）

## してはいけないこと

- 出た候補を機械的に全部直す。**意図的な使い分けを潰す**
- 「似ている」だけで括る。片方だけ将来変わるものを一本化すると、分けるより高くつく
- **道具の誤検出を「所見なし」と読む。** この道具自身、最初の版は Rust の
  メソッド呼び出しを数え落として健全な `pub` を40件並べ、文字リテラル `'"'` に
  引っかかってコードを消していた。**件数が急に減ったら、直ったのか壊れたのかを
  確かめる**
- 目視で「きれいでした」と報告する。**測っていないなら測っていないと言う**
